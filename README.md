# OS CPU Scheduling Tutor: RAG + Instruction-Tuned LLM + Simulator

R G Rishon · 24BCE2061 · Operating Systems Lab Project

A tutor chatbot for the CPU Scheduling unit. Explanations come from course
material (retrieval-augmented generation). Numerical answers come from a
deterministic scheduling simulator, so they are **computed, not generated**.

## Quick start

```bash
pip install streamlit matplotlib pandas
python run_demo_checks.py        # every line should say PASS
streamlit run app.py             # opens at localhost:8501
```

Everything runs offline on the laptop. No GPU, API key or network needed.

## What the app does

| Tab | What it shows |
|---|---|
| 💬 Tutor | Chat. The router sends numerical questions to the simulator and concept questions to retrieval. Every answer shows its sources, and off-topic questions are refused. |
| 🧮 Simulator | Editable process table → Gantt chart, per-process times, step-by-step decision log, and all 6 algorithms compared on the same data. |
| 📝 Practice | New problems, each solved by the simulator and re-parsed by the router before being shown. Students can check their own answer. |
| ✅ Check my answer | Paste a question and your working. The tutor pinpoints the **first step** where your calculation diverges and says why. |
| 📊 Pipeline & evaluation | Dataset composition, knowledge-base sources, and a one-click evaluation on the held-out set. |

## Enabling the LLM

The tutor uses the first Ollama model it finds from: `$OSTUTOR_MODEL`,
`ostutor` (the fine-tuned model), `qwen2.5:3b-instruct`, `qwen3:4b`, `qwen3:8b`.
If none is running it uses **grounded template mode**. The numbers still come
from the simulator and the explanations are quoted, with citations, from the
retrieved course material, so nothing is made up.

```bash
ollama pull qwen2.5:3b-instruct  # base model, ~1.9 GB, used by default
# or, after Colab fine-tuning:
ollama create ostutor -f finetune/Modelfile
```

Note: `qwen3:4b` is a "thinking" model — on CPU-only hardware it spends a
long time reasoning before answering (over a minute even for a one-word
reply), so `qwen2.5:3b-instruct` is preferred by default for interactive use.

## Web pages (optional): `rag/`

```bash
python -m rag.fetch_gfg        # saves 9 GeeksforGeeks scheduling articles to corpus/web/geeksforgeeks/
python build_index.py          # re-index
```
`rag/fetch_wiki.py` checks robots.txt, identifies itself honestly, waits between requests, keeps only the
article text, and writes a `.meta.json` (url, date, licence note) beside each page. These pages say
"All rights reserved": they are kept **for your own study and local retrieval only**, are not part of the
zip, and must not be published with the project.

**How the app uses them.** Your vetted notes always supply the answer. A GeeksforGeeks passage is added only when it
is about the same algorithm as the question, speaks to the specific thing asked, and says something the answer does
not (example problems, summaries, table rows and anything with the opposite priority convention are never used):
- under a stored answer: an optional **"📚 More detail from GeeksforGeeks"** card with one short quote and a link;
- in a model-written answer: up to two passages are offered to the model as unvetted extra material, and if the
  answer cites one, a note says so.
Analogy and formula questions never get a card. Scraped text is untitled in the index, so it can never be shown
as a vetted Q&A.

## Knowledge base

`corpus/notes/` holds course notes in the textbook's conventions.
`corpus/ostep/` holds the OSTEP CPU chapters (free online, by the authors).

## Verification and evaluation

* **Numbers** come only from `scheduler.py`; every result is re-checked against the definitions (`check_invariants`) and, in
  tests, against an independent reference simulator (`eval/reference_sim.py`). Conventions: lower priority number = higher
  priority; ties by arrival, then input order; preemptive algorithms preempt only for a strictly better key; Round Robin queues an
  arrival at a quantum boundary before the preempted process; context switches cost zero time; invalid input is rejected.
* **Concept answers** from the model go through `concept_check.py` (fact rules, contradictions, unsupported claims, missing
  essential points); a failed check is regenerated once, then replaced by the vetted course text. Failures are logged to
  `logs/verification.jsonl`.
* Each answer carries an honest `status` shown in the app (verified / fact-checked / vetted text / nothing to verify).
* `python -m eval.run_eval` runs the 185-case evaluation suite; see `eval/README.md`.
